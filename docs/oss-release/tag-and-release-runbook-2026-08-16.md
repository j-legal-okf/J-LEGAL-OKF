# Tag-and-release runbook (v0.1.0-draft.1)

Status: **specification only**. Nothing in this document has been applied.
It exists so the day the maintainer cuts `v0.1.0-draft.1` can be executed
mechanically, without re-deriving which sentences flip from true to false at
that moment.

This is change set B from the plan `sprightly-hatching-token.md`
("公開前の矛盾解消"). Change set A (2026-08-16) intentionally left every
sentence in this document untouched, because each one is true today and
false the moment a tag exists — flipping it early would have made it false
now instead of tomorrow.

Owner decisions this runbook assumes (recorded 2026-08-16, in the plan):
tag name `v0.1.0-draft.1`; package version bumped to `0.1.0.dev1` and
already applied by change set A; **no release artifacts are attached** — the
release carries notes only; PyPI is not used for this release.

This document cites no line numbers. An earlier draft did, and an audit
measured two of the four as already wrong on the day they were written — a
runbook is executed later than it is authored, so a line number in one is a
stale reference waiting to happen. Every target below is quoted verbatim
instead. Locate it by searching for the quoted text; if the text no longer
matches, re-read the surrounding paragraph rather than editing blind.

## 1. `CHANGELOG.md`

1. Change the section heading `## [Unreleased]` to
   `## [0.1.0-draft.1] - <YYYY-MM-DD>` (the actual tag date), keeping every
   entry currently under it in place.
2. Immediately above the renamed heading, insert a new, empty
   `## [Unreleased]` section (heading only — no body line under it yet;
   add one only once new unreleased work exists).
3. Delete the sentence "Nothing has been tagged or released yet." — the only
   body line under the `## [Unreleased]` heading it described. This is the one
   sentence change set A deliberately did not touch, because it is the single
   place release state is asserted and it was still true when change set A
   ran.
4. Update the link-reference definition at the bottom of the file,
   `[Unreleased]: https://github.com/j-legal-okf/J-LEGAL-OKF/commits/main`,
   to two definitions:
   - `[Unreleased]: https://github.com/j-legal-okf/J-LEGAL-OKF/compare/v0.1.0-draft.1...main`
   - `[0.1.0-draft.1]: https://github.com/j-legal-okf/J-LEGAL-OKF/releases/tag/v0.1.0-draft.1`

After this edit, `tools/check_release_state.py` still passes unchanged: it
exempts `CHANGELOG.md` from the scan, so removing that file's assertion of
release state requires no change to the checker. Re-run it after editing —
it is the `boundary` job in CI, and it takes under a second locally.

## 2. `SECURITY.md`

Currently, under `## Reporting a vulnerability`:

> Use GitHub's private vulnerability reporting on
> [`j-legal-okf/J-LEGAL-OKF`](https://github.com/j-legal-okf/J-LEGAL-OKF)
> (Security tab → Report a vulnerability). This feature must be enabled on
> the repository by the maintainer, and until the repository is public and
> the feature is enabled, this reporting channel may not be available.

**Do not edit this file until private vulnerability reporting has actually
been enabled on the repository** (see §4 below — that is a GitHub settings
change, not a file edit, and needs its own approval). Once enabled, replace
the last sentence ("This feature must be enabled... may not be available.")
with a plain statement that the channel is enabled, and remove the
visibility-conditional wording. Enabling the feature without editing the
file is a safe intermediate state — the sentence becomes overly cautious,
not false — but do not edit the file while the feature is still disabled;
that would make it false.

## 3. `CODE_OF_CONDUCT.md`

Currently, in the bulleted list of what is and is not available:

> - Once this repository is public and the feature is enabled, the
>   repository's private security advisory form under the Security tab
>   exists, but it is scoped to security vulnerability reports rather than
>   conduct reports.
> - Making this repository public does not add such a channel. If one is

Same gate as §2: only edit after private vulnerability reporting is
actually enabled. At that point, change "Once this repository is public and
the feature is enabled" to a plain present-tense statement that the form
exists (still scoped to security reports, not conduct reports — this
document's point is that conduct reports have no channel yet, which remains
true independent of visibility).

## 4. GitHub repository settings (separate approval from Public化)

Both of the following are GitHub settings changes on
`j-legal-okf/J-LEGAL-OKF`, not file edits, and each needs its own explicit
approval per `jlegal-oss-separation-management`'s Git-work rules. Neither is
authorized by this document or by change set A's commit approval.

1. **Branch protection on `main`**: require a pull request before merging,
   and add `dco` (the job defined in `.github/workflows/ci.yml`) as a
   required status check. This makes the DCO check something a contributor
   cannot bypass by pushing directly, matching what `GOVERNANCE.md`
   already claims about every commit needing a `Signed-off-by` trailer.
2. **Private vulnerability reporting**: enable it under the repository's
   Security tab. Do §2 and §3 above only after this is confirmed enabled,
   not before and not at the same time without confirming first.

## 5. Release artifacts (owner decision: none attached)

The owner decision recorded in the plan is that v0.1 ships as **release
notes only** — no attached files, no PyPI publication. Concretely:

- Do **not** add an `upload-artifact` step or a publish step to the
  `package-distribution` job in `.github/workflows/ci.yml`. That job stays
  verification-only: it builds the sdist/wheel, checks them against
  `tools/verify_distribution.py`'s allowlist, and installs+tests from both,
  exactly as it does today. Its purpose is proving the distribution is
  clean, not producing something to attach.
- When creating the GitHub release for the `v0.1.0-draft.1` tag, write
  release notes (a summary, not a copy of the full `CHANGELOG.md` entry)
  and attach nothing.
- Do not register or upload to PyPI. If this decision changes later, it is
  a new, separately reviewed and approved change, not an extension of this
  runbook.

## 6. Order of operations

1. Confirm the change set A commit (README/CHANGELOG/GOVERNANCE/SECURITY/
   okf/project.md/tests, this runbook) is merged to `main`.
2. Get the two separate GitHub-settings approvals in §4, execute them, and
   confirm private vulnerability reporting is enabled before touching any
   file in §2 or §3.
3. Edit `SECURITY.md` and `CODE_OF_CONDUCT.md` per §2-3, in their own commit
   (or the same commit as the tag-prep `CHANGELOG.md` edit — either is fine,
   but do not combine with unrelated changes).
4. Edit `CHANGELOG.md` per §1.
5. Re-run the full verification matrix from
   `sprightly-hatching-token.md` ("検証" section) against the result before
   tagging: public suite, `tools/check_boundary.py`,
   `tools/check_release_state.py`, `jlegal --version` /
   `python -m jlegal_okf --version`, and the determinism check.
6. Tag creation and the GitHub release itself are their own explicit
   approvals, per `jlegal-oss-separation-management`'s Git-work rules — this
   runbook prepares the tree for them but does not authorize them.
