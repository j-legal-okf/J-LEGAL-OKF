# v0.1 Implementation Review — Final Questions, Answered

## Status and scope

This document introduces no new facts, no new behavior, and no new
identifier, rule, or diagnostic code. It answers, in order, the final
review-question checklist from the project's v0.1 implementation review by
pointing at what already exists in this repository: the reference
implementation (`src/jlegal_okf/`), the normative profile and its satellite
docs, and the offline regression tests. Where a claim below needs a citation,
the citation is a file path and line range, a doc anchor, or a test name —
never a restatement without one. Every code identifier, function name, and
test name cited below was opened and read in this checkout before being
cited; every named test was individually executed against this checkout and
passed (see "Verification" at the end of this document).

The fifteen questions are reproduced below in the review's own order, each
rewritten in this project's own words rather than quoted from the source
document. Nothing in this document changes `docs/jlegal-okf-profile-0.1.0-draft.md`,
which remains the sole normative contract; where this document and the
profile could be read to disagree, the profile controls.

## Q1. Where is the original source text preserved?

Two separate, independently verified preservation contracts exist for this,
not one (`docs/jlegal-okf-profile-0.1.0-draft.md`, ["Preservation
levels"](jlegal-okf-profile-0.1.0-draft.md#preservation-levels)):

- **Byte layer (rule `JLEGAL-BYTE-PRESERVE-1`).** The exact bytes read from
  disk are hashed and, on export, embedded verbatim as
  `references/source.xml` inside the OKF bundle. `admit_egov_xml` computes
  `source_sha256=hashlib.sha256(raw).hexdigest()` directly off the bytes read
  from the input file, with no decoding step in between
  (`src/jlegal_okf/egov.py` `admit_egov_xml()`). `_source_reference` writes those same
  bytes, unmodified, to `references/source.xml` after checking the caller's
  file hash against the corpus's declared source
  (`src/jlegal_okf/legal_okf.py` `_source_reference()`, hash check at lines 140-141).
- **Character layer (rule `JLEGAL-TEXT-PRESERVE-1`).** Every `LegalNode.text`
  is the source element's character data, rendered verbatim by `_render_text`
  walking the parsed XML tree and eliding only pure XML-formatting
  whitespace (`src/jlegal_okf/egov.py` `_render_text()`). `LegalNode` itself is
  immutable (`@dataclass(frozen=True)`, `src/jlegal_okf/model.py` `LegalNode`).
  One documented exception qualifies the "verbatim" above: a structural node
  with no character data of its own carries that element's XML serialization
  as `text` rather than an empty string, a source/canonical conflation the
  profile records as a known limitation and does not resolve in this revision
  (`docs/jlegal-okf-profile-0.1.0-draft.md:155-165`).

Verified: `tests/test_regression_contracts.py::test_byte_preservation_embeds_exact_source_bytes`
compiles a fixture, exports a bundle, and asserts the embedded
`references/source.xml` bytes equal the original file's bytes.

## Q2. How is it verified that the source text was not altered?

Two levels, matching the two preservation layers above:

- **Hash agreement (default, cheap).** `SourceRef.sha256` is checked for
  well-formedness at construction (`src/jlegal_okf/model.py` `SourceRef`,
  `SOURCE_SHA256` at line 150) and cross-checked at every read/write
  boundary: `export_okf` refuses a caller-supplied source file whose hash
  disagrees with the corpus's declared source (`JLEGAL_OKF_SOURCE_MISMATCH`,
  `src/jlegal_okf/legal_okf.py` `_source_reference()`), and `validate_okf`'s default check
  re-hashes the bundle's own embedded `references/source.xml` against the
  nodes' declared `source.sha256` (`JLEGAL_OKF_SOURCE_TAMPERED`,
  `src/jlegal_okf/legal_okf.py` `_validate_source_reference()`).
- **Full re-derivation (`--verify-source`, deliberately optional and
  stronger).** Hash agreement alone only proves internal self-consistency —
  a corpus hand-edited after compile, with every dependent hash
  recomputed, still agrees with itself. `validate_okf(bundle,
  verify_source=True)` closes that gap: it re-converts the bundle's embedded
  `references/source.xml` through the declared adapter and build recipe and
  byte-compares the result against the bundle's own
  `canonical/corpus.jsonl`/`crosswalk.jsonl`/`projection.jsonl`
  (`src/jlegal_okf/legal_okf.py` `validate_okf()`, reusing
  `verify_manifest(..., verify_inputs=True)` at
  `src/jlegal_okf/pipeline.py` `verify_manifest()`).

Verified:
`tests/test_regression_contracts.py::test_validate_okf_verify_source_catches_a_corpus_not_derived_from_source`
constructs exactly that internally-self-consistent-but-tampered bundle,
confirms plain `validate_okf(bundle)` still accepts it, and confirms
`validate_okf(bundle, verify_source=True)` rejects it with
`JLEGAL_OKF_CANONICAL`.

## Q3. Where is the article/paragraph/item hierarchy represented?

`NodeKind` (`src/jlegal_okf/model.py` `NodeKind`) enumerates every structural
level the reviewed e-Gov hierarchy defines (article, paragraph, item,
subitem, and so on). Each `LegalNode` carries `parent_id`, `depth`, and a
canonical `locator` path (`src/jlegal_okf/model.py` `LegalNode`) built by
`semantic_locator` (`src/jlegal_okf/model.py` `semantic_locator()`); the adapter walks the
source XML tree recursively and creates one node per recognized structural
element, threading `parent_id`/`depth`/`locator` down the recursion
(`egov_xml_adapter`'s `visit_children`, `src/jlegal_okf/egov.py` `egov_xml_adapter()`).
This is never flattened to prose or Markdown — Markdown output is a
projection, not the canonical form (profile
["Preservation and scope"](jlegal-okf-profile-0.1.0-draft.md#preservation-and-scope)).

The hierarchy is not merely produced once and trusted; it is re-verified on
every `validate_corpus` call. The structure layer's diagnostics
(`docs/validator-layers.md`, "2. Structure") check parent/child well-formedness
independently of how the tree was built: `ROOT_KIND`/`ROOT_DEPTH` (a
parentless node must be `LAW` at `depth == 0`), `PARENT_DEPTH`/`PARENT_MISSING`
(a child's declared parent must exist and be exactly one level shallower),
`KIND_TRANSITION` (only specific parent→child kind pairs are allowed — the
`_ALLOWED` table, `src/jlegal_okf/validation.py` `_ALLOWED`), and `TREE_CYCLE`/
`TREE_UNREACHABLE` (walking `parent_id` must terminate at a root, never loop
or dead-end) — all in `src/jlegal_okf/validation.py` `collect_diagnostics()`.

Verified: `tests/test_regression_contracts.py::test_ids_versions_and_diagnostics_are_stable`
asserts `ROOT_KIND` fires on a mis-kinded root node, exercising this layer
directly.

## Q4. How is "Article 12-2" distinguished from "Article 12, Paragraph 2"?

By keeping two different concepts in two different fields, never conflated.
A branch article (第12条の2) is one `ARTICLE` node with `ordinal=12,
branch=(2,)`; a paragraph (第12条第2項) is a separate child node of kind
`PARAGRAPH` with its own `ordinal=2`, nested one level under the `ARTICLE`
node (`_ALLOWED[NodeKind.ARTICLE] == {PARAGRAPH, ITEM, TABLE}`,
`src/jlegal_okf/validation.py` `_ALLOWED`). `branch` is always a tuple of positive
`int`s (rejected otherwise — `NODE_BRANCH`,
`src/jlegal_okf/model.py` `LegalNode`), never a decimal — "12-2" is never turned into
"12.2" (rule `JLEGAL-NORM-3`,
[`docs/normalization-rules.md`](normalization-rules.md#jlegal-norm-3-ordinalbranch-decomposition),
implemented by `_ordinal_branch`, `src/jlegal_okf/egov.py` `_ordinal_branch()`, which
handles ASCII digit-hyphen form, plain digits, and kanji numerals as three
separate input shapes, always returning `(ordinal, branch_tuple)`).

Verified:
`tests/test_regression_contracts.py::test_egov_hierarchy_temporal_and_fail_closed_contracts`
asserts `Num="3-2"` compiles to `article.ordinal == 3, article.branch == (2,)`;
`tests/test_regression_contracts.py::test_egov_kanji_numeral_ordinal_and_branch_fallback`
asserts the kanji fallback (`第十二条の二`, no `Num` attribute) compiles to
`(ordinal, branch) == (12, (2,))`.

## Q5. Where are source and retrieval time recorded?

Two different scopes, deliberately not merged:

- **Per-node source identity**: `SourceRef` on every `LegalNode`
  (`uri`, `sha256`, `adapter`, `source_key`,
  `src/jlegal_okf/model.py` `SourceRef`) — a content-addressed pointer to the
  exact bytes that node was derived from, never a filesystem path
  (`content_addressed_uri`, `src/jlegal_okf/model.py` `content_addressed_uri()`).
- **Acquisition provenance** (retrieval URL and UTC timestamp): recorded
  only when the caller supplies a `jlegal fetch --receipt-out` receipt
  (`FetchResult.acquisition()`, `src/jlegal_okf/egov.py` `FetchResult`), carried
  into `manifest.json`'s `acquisition` record
  (`_egov_acquisition`, `src/jlegal_okf/pipeline.py` `_egov_acquisition()`). A saved XML
  compiled without a receipt keeps `source_url` and `retrieved_at` `null`
  and never infers them from file mtime or compile time
  (`_base_source_metadata`, `src/jlegal_okf/egov.py` `_base_source_metadata()`, `source_url`/
  `retrieved_at` set to `None` at lines 562-563; see also
  [`docs/known-limitations.md`, "3. Acquisition provenance"](known-limitations.md#3-acquisition-provenance)
  and [README, "e-Gov acquisition provenance"](../README.md#e-gov-acquisition-provenance)).

Verified:
`tests/test_regression_contracts.py::test_fetch_receipt_is_verified_and_propagated_to_okf_frontmatter`
fetches through a mocked HTTP response, writes a receipt, compiles with it,
and asserts `manifest["acquisition"]["source_url"]` starts with
`https://laws.e-gov.go.jp/api/2/law_data/` and
`manifest["acquisition"]["retrieved_at"]` ends with `"Z"`.

## Q6. Can the spec version used for a given conversion be determined?

Yes. `manifest.json`'s `conversion` record is a fixed, versioned constant —
`JLEGAL_CONVERTER = {"name": "JORI Engine", "version": "0.1.0-draft",
"profile": "J-LEGAL-OKF/0.1.0-draft"}` (`src/jlegal_okf/pipeline.py` `JLEGAL_CONVERTER`) —
written into every `egov_xml` compile's manifest
(`manifest_for`, `src/jlegal_okf/pipeline.py` `manifest_for()`) and copied into every
exported concept file's YAML frontmatter (`_source_frontmatter`/
`_derived_frontmatter`, `src/jlegal_okf/legal_okf.py` `_source_frontmatter()`; `src/jlegal_okf/legal_okf.py` `_derived_frontmatter()`). The manifest
and bundle schemas are themselves versioned strings —
`jori-corpus/v1` (`src/jlegal_okf/model.py` `SCHEMA`), `jori-manifest/v5`/`v6`
(`src/jlegal_okf/pipeline.py` `_MANIFEST_SCHEMA`; `src/jlegal_okf/pipeline.py` `_MANIFEST_SCHEMA_RIGHTS`), `jori-projection/v1`
(`RetrievalDocument.to_dict`, `src/jlegal_okf/model.py` `RetrievalDocument`), and
`jlegal-okf-bundle/v1`/`v2` (`src/jlegal_okf/legal_okf.py` `BUNDLE_SCHEMA`; `src/jlegal_okf/legal_okf.py` `BUNDLE_SCHEMA_RIGHTS`) — so a
consumer can distinguish which manifest/bundle *shape* it is reading even
without inspecting the `conversion` record.

Verified:
`tests/test_synthetic_golden_matrix.py::test_structure_matrix_matches_fixed_golden_and_replays_from_bundle`
asserts `manifest["conversion"] == {"name": "JORI Engine", "profile":
"J-LEGAL-OKF/0.1.0-draft", "version": "0.1.0-draft"}` and
`manifest["schema"] == "jori-manifest/v5"` on a real compile.

## Q7. Where is LLM-generated information kept separate from source/canonical data?

Structurally, not just by policy: no code path in this repository produces
LLM output at all. Every module under `src/jlegal_okf/` was read for this
review (`__init__.py`, `__main__.py`, `adapters.py`, `cli.py`, `egov.py`,
`errors.py`, `legal_okf.py`, `model.py`, `pipeline.py`, `validation.py`);
none imports an LLM/model-provider client, and `pyproject.toml`'s
dependencies are exactly `defusedxml`, `httpx`, `PyYAML` (runtime) and
`pytest` (dev) — no LLM SDK.

What exists instead is the boundary an LLM-producing overlay would have to
respect. An exported OKF bundle keeps a dedicated `derived/` directory whose
single file, `derived/knowledge.md`, is generated with
`content_policy: "none-generated"` and body text stating plainly that "This
bundle contains no model-generated legal interpretation, summary, or advice"
(`_derived_frontmatter`, `src/jlegal_okf/legal_okf.py` `_derived_frontmatter()`; written by
`export_okf` at `src/jlegal_okf/legal_okf.py` `export_okf()`; re-checked byte-for-byte
by `_validate_derived` on every `validate_okf` call,
`src/jlegal_okf/legal_okf.py` `_validate_derived()`). Each per-node concept file's
frontmatter is tagged `"layer": "source"` (`src/jlegal_okf/legal_okf.py` `_source_frontmatter()`)
against the boundary file's `"layer": "derived"`
(`src/jlegal_okf/legal_okf.py` `_derived_frontmatter()`) — a machine-checked field, not only a
naming convention. At the design-principle level,
[`ARCHITECTURE_BOUNDARY.md`](../ARCHITECTURE_BOUNDARY.md) states that
"[generated or model-derived output] is non-deterministic or model-dependent
output that cannot serve as evidence" and stays out of the public core
(lines 38-40), and that "Generated or model-derived knowledge is never
source or canonical evidence, in the public core or anywhere that consumes
it" (lines 55-57). `docs/known-limitations.md`'s closing section,
["Scope: LLM audition is not part of
v0.1"](known-limitations.md#scope-llm-audition-is-not-part-of-v01), states
this is a Private-overlay responsibility, not a v0.1 deliverable.

## Q8. Can the basic bundle still be produced if the LLM is unavailable?

Yes — trivially, because nothing in v0.1's compile→validate→export→validate
pipeline calls an LLM at any point (see Q7). The full pipeline is exercised
completely offline, with no network or model dependency, in
`tests/test_public_core.py::test_public_synthetic_fixture_drives_cli_end_to_end`
and in the CI step named `Run offline synthetic example (README "Offline
synthetic example")` in the `cli-e2e` job of
[`.github/workflows/ci.yml`](../.github/workflows/ci.yml), which runs
`jlegal validate-source` → `compile` → `validate` → `export-okf` →
`validate-okf` against `examples/synthetic_egov_law.xml` with no
credentials, API key, or network call involved. The profile's
["Exclusions"](jlegal-okf-profile-0.1.0-draft.md#exclusions) section states
this directly: "LLM execution and audition specifically remain the
independent responsibility of a Private overlay; they are not part of
v0.1's required public-core implementation."

## Q9. How are conversion omissions detected?

By fail-closed admission before any node is built, not by best-effort
flattening. `_ensure_supported_tree` walks the entire source XML tree ahead
of conversion and raises `AdapterError("EGOV_XML_UNSUPPORTED_STRUCTURE:<tag>")`
for any element outside the reviewed tag set (`_KNOWN_TAGS`) that has
children (`src/jlegal_okf/egov.py` `_ensure_supported_tree()`). `NewProvision` specifically is
always rejected, including an empty `<NewProvision/>` wrapper, rather than
being silently flattened into its parent's text (`_FAIL_CLOSED_TAGS =
{"NewProvision"}`, `src/jlegal_okf/egov.py` `_FAIL_CLOSED_TAGS`, checked at line 443-444).
Admission additionally refuses a structurally empty `LawBody` — a document
whose body contains no recognized structural element at all
(`EGOV_XML_STRUCTURE_EMPTY`, `src/jlegal_okf/egov.py` `admit_egov_xml()`, re-checked
after the tree walk at line 668-669). This is the same admission function
`jlegal validate-source` and the adapter itself both call, so admission
cannot be bypassed by skipping the standalone pre-check
(`docs/jlegal-okf-profile-0.1.0-draft.md`,
["Preservation and scope"](jlegal-okf-profile-0.1.0-draft.md#preservation-and-scope)).

Verified: `tests/test_public_core.py::test_egov_rejects_new_provision` and
the unsupported-structure case in
`tests/test_regression_contracts.py::test_egov_hierarchy_temporal_and_fail_closed_contracts`
both assert `AdapterError` with `EGOV_XML_UNSUPPORTED_STRUCTURE:NewProvision`.

## Q10. How is drift from the source detected after the fact?

This is the same mechanism as Q2, applied to a corpus/bundle that may have
been produced or edited outside this project's own compile step: default
`validate_okf`/`verify_manifest` catch internal inconsistency (a declared
hash that disagrees with the bytes actually on disk —
`MANIFEST_CORPUS_TAMPERED`, `JLEGAL_OKF_CANONICAL_TAMPERED`, and similar,
throughout `src/jlegal_okf/pipeline.py` `verify_manifest()` and
`src/jlegal_okf/legal_okf.py` `validate_okf()`), but cannot by itself prove the
canonical corpus was *actually derived* from the embedded source XML, only
that its own declared hashes agree with each other. `--verify-source` closes
that gap by re-running the real conversion and byte-comparing the result
(see Q2). The profile states this distinction explicitly: "The default
`validate-okf` (no flag) only confirms that a bundle's declared hashes agree
with each other and with its own files; it does not prove the canonical
corpus was actually produced by converting the embedded source"
(`docs/jlegal-okf-profile-0.1.0-draft.md`,
["Preservation and
scope"](jlegal-okf-profile-0.1.0-draft.md#preservation-and-scope), lines
99-102).

Verified: same test as Q2,
`tests/test_regression_contracts.py::test_validate_okf_verify_source_catches_a_corpus_not_derived_from_source`.

## Q11. Are stable error/diagnostic codes returned on failure?

Yes, at two levels. **Exceptions** raised anywhere in the pipeline carry a
short, stable, uppercase string code as their message — `AdapterError`,
`ValidationError`, `JLegalError` (`src/jlegal_okf/errors.py` `AdapterError`; `src/jlegal_okf/errors.py` `ValidationError`; `src/jlegal_okf/errors.py` `JLegalError`), and
`LegalOKFError` (`src/jlegal_okf/legal_okf.py` `LegalOKFError`) — for example
`EGOV_XML_UNSUPPORTED_STRUCTURE:<tag>`, `MANIFEST_CORPUS_TAMPERED`,
`JLEGAL_OKF_SOURCE_MISMATCH`; these are not free-form messages, they are
grepped for in this project's own tests (`pytest.raises(..., match=...)`)
throughout `tests/test_regression_contracts.py`. **Corpus validation**
additionally returns a structured `Diagnostic(code, subject, detail)` tuple
(`src/jlegal_okf/validation.py` `Diagnostic`) drawn from 36 stable codes, each
mapped to one of four validator layers via `DIAGNOSTIC_LAYERS`
(`src/jlegal_okf/validation.py` `DIAGNOSTIC_LAYERS`), with `Diagnostic.to_dict()` including
that `"layer"` — documented one-to-one in
[`docs/validator-layers.md`](validator-layers.md) and kept from drifting by
`tests/test_validator_layers.py`, which compares the doc's per-section code
table, `DIAGNOSTIC_LAYERS`, and the codes `validation.py` can actually emit,
three ways. At the CLI boundary, `jlegal validate --diagnostics-json` prints
the full diagnostic array and exits 2 if non-empty
(`src/jlegal_okf/cli.py` `_validate()`), and `main()`'s top-level handler maps
`AdapterError`/`ValidationError`/`LegalOKFError`/`ValueError`/`KeyError`/
`json.JSONDecodeError` to exit code 2 and `JLegalError`/`OSError` to exit
code 3 (`src/jlegal_okf/cli.py` `main()`) — a stable mapping, not incidental.

Verified: `tests/test_regression_contracts.py::test_cli_exit_codes_are_stable`
asserts a malformed `compile` invocation exits 2 and a `validate` against a
missing corpus exits 3;
`tests/test_validator_layers.py::test_diagnostic_to_dict_includes_its_layer`
asserts a `Diagnostic`'s `to_dict()` includes its layer.

## Q12. Is the basic output stable for a given input (i.e. deterministic)?

Yes, verified at three separate granularities, and enforced in CI, not only
in local tests:

- **Same directory, same input, twice**: byte-identical `corpus.jsonl`, and
  a second compile into the same output directory is refused outright
  (`OUTPUT_EXISTS_REFUSED`) rather than silently overwritten —
  `tests/test_regression_contracts.py::test_compile_is_deterministic_and_refuses_existing_output`.
- **Different working directories, same bytes and `corpus_id`**:
  byte-identical `corpus.jsonl`/`crosswalk.jsonl`/`projection.jsonl`/
  `manifest.json`, because `source.uri` is content-addressed and never a
  local path (`content_addressed_uri`, `src/jlegal_okf/model.py` `content_addressed_uri()`) —
  `tests/test_regression_contracts.py::test_compile_is_path_independent`.
- **Same bytes, two different wall-clock compile times**: every
  deterministic hash (`corpus_sha256`, `crosswalk_sha256`,
  `projection_sha256`, `build_options_sha256`) is identical; only
  `manifest.json`'s `converted_at` field itself differs, because
  `converted_at` is deliberately excluded from the payload that
  `build_options_sha256` hashes (`src/jlegal_okf/pipeline.py` `manifest_for()`) —
  `tests/test_regression_contracts.py::test_converted_at_is_excluded_from_deterministic_hashes`.

This is also a CI gate, not only a local assertion: the "Determinism check"
job compiles the same fixture twice into separate output directories and
diffs `corpus.jsonl`/`crosswalk.jsonl`/`projection.jsonl` byte-for-byte,
failing the workflow on any difference: the CI step named
`Determinism check (compile output, byte-for-byte)` in the `cli-e2e` job of
[`.github/workflows/ci.yml`](../.github/workflows/ci.yml).

Yes, as a dedicated, single-purpose document:
[`docs/known-limitations.md`](known-limitations.md), organized into four
numbered sections (supported structure, input parsing posture, acquisition
provenance, temporal relations) plus a closing LLM-audition scope statement,

One inconsistency worth flagging here rather than silently fixing (this
document does not edit other files): `CHANGELOG.md:236` still states "There
is no continuous integration yet," but
[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) exists, runs on

offline CLI end-to-end job, a determinism check, and a package-distribution
build/verify job. That `CHANGELOG.md` line appears to predate the workflow
file and was not updated when it was added.

## Q14. Do the test cases include hard structures drawn from real statutes?

The hard structures are covered; the text carrying them is authored rather
than taken from a real statute, and that substitution is a deliberate,
documented rights decision rather than a capability gap.
[`ARCHITECTURE_BOUNDARY.md`](../ARCHITECTURE_BOUNDARY.md) states the
governing principle — something stays out of the public core when "[i]t
depends on acquired or licensed data whose redistribution is not
established" (lines 32-33) — and
[`docs/licensing-and-attribution.md`](licensing-and-attribution.md) records
that this project has not resolved that question for real law text: it has
"not evaluated how [Copyright Act Article 13, item 1] applies to any
specific law text or e-Gov XML content", leaving that "to whoever approves
inclusion of specific real-law material in this project, on a case-by-case
basis" (lines 209-216). The same document does not license a user's
downstream use either; it states that output produced by running this tool
against real e-Gov data "is not part of this repository and is the
downstream user's own responsibility to license correctly" (lines 305-307),
and then gives attribution guidance for it.
[`docs/synthetic-golden-matrix.md`](synthetic-golden-matrix.md) records the
resulting choice: an entirely invented fixture,
[`examples/fixtures/synthetic_egov_structure_matrix.xml`](../examples/fixtures/synthetic_egov_structure_matrix.xml),
schema-checked against the official e-Gov XML Schema v3 as an independent,
manual step (documented, not run in CI —
[`docs/synthetic-golden-matrix.md`, "Official XSD
check"](synthetic-golden-matrix.md#official-xsd-check)).

The fixture XML
(`examples/fixtures/synthetic_egov_structure_matrix.xml`) and the test that
exercises it
(`tests/test_synthetic_golden_matrix.py::test_structure_matrix_matches_fixed_golden_and_replays_from_bundle`)
were both read in full for this review. The test asserts exactly 16 named
coverage cases, one assertion function each,
listed in `docs/synthetic-golden-matrix.md` and cross-checked in the test
itself (`EXPECTED_COVERAGE`, `tests/test_synthetic_golden_matrix.py` `EXPECTED_COVERAGE`):
gaps in article numbering, a deleted article (`Delete="true"`), a branch
article (第三条の二), an article whose first paragraph is numbered
internally but has an empty display number, three い・ろ・は subitems under
one item, supplementary provisions, an appendix table and an appendix style
sharing the same `Num="1"` under one parent (resolved to two distinct
`node_id`s via rule `JLEGAL-NORM-5`), a table structure, a sentence
asserting multiple effective dates in one supplementary-provision paragraph,
a transitional-measure article, and one sentence each for reference,
incorporation (準用), read-as (読み替え), and delegation (委任) wording, plus
an amendment supplementary provision (`Type="Amend"`) with an
`AmendProvision` child. All 16 are asserted structurally (locator, ordinal,
branch, parent/child relation, or exact preserved text), not merely present.

For real e-Gov law text specifically: this repository's tracked files carry
no e-Gov law data (confirmed by
[`docs/licensing-and-attribution.md`, "This repository's data
content"](licensing-and-attribution.md#this-repositorys-data-content),
which states this was checked by enumerating every tracked `.xml` file).
Verification against real, published law text is carried out outside this
repository, under a separate, repeatable procedure, and the record that such
verification was performed is retained as part of this project's own
release history — consistent with the "Guidance for downstream users"
section of `docs/licensing-and-attribution.md`, which already tells a user
running this tool against real e-Gov data how to attribute and disclose
processing of that output. Run counts and content digests from that external
verification are deliberately not restated here: quoting them would turn
this document into their publication point, and a reader could not check
them against anything this repository ships.

**What is not covered by name in the 16-item list**, stated plainly rather
than folded into the "compliant" claim above: the fixture has no dedicated
case for a long parenthetical/bracketed clause as its own coverage id, no
case exercising `Part`/`Chapter`/`Section` nesting as a *named* hard case
(chapter-level nesting support exists and is exercised incidentally by
`SupplProvision`/`Chapter` nesting in
`tests/test_regression_contracts.py::test_egov_hierarchy_temporal_and_fail_closed_contracts`,
but not as a structure-matrix coverage id), and no case using the specific
"前条"/"次の各号" self-referencing wording — the fixture's
`reference_sentence`/`incorporation_sentence` cases use a fixed article
citation ("第三条の二の規定を...") rather than a relative one.

Two of those three are gaps in the *named coverage list* only: a long
parenthetical and a relative-reference phrase are ordinary sentence text,
preserved verbatim regardless of content by rule
`JLEGAL-TEXT-PRESERVE-1`, so no structural support is missing. The third is
weaker than that and is stated here rather than folded in: `Part` and
`Section` are structural node kinds, not text, and while `_NODE_TAGS` maps
both (`src/jlegal_okf/egov.py` `_NODE_TAGS`), **neither tag occurs in any
fixture or test in this repository** — `Chapter` is converted exactly once,
in `test_egov_hierarchy_temporal_and_fail_closed_contracts`. Their handling
is therefore implemented but unexercised. This is the same fact
`CHANGELOG.md:274-275` records more briefly ("The synthetic fixture
exercises only a small part of the reviewed hierarchy").

## Q15. Would adding municipal-ordinance input later avoid breaking the core design?

Yes, by the same public-core/private-boundary principles this project
already applies to everything else, not by a special carve-out written for
this question.
[`ARCHITECTURE_BOUNDARY.md`](../ARCHITECTURE_BOUNDARY.md) states the
principles for what belongs in the public core — deterministic and
reproducible from published inputs, third-party verifiable, a stability
contract, demonstrable with authored synthetic fixtures (lines 10-27) — and
for what stays out — data of unconfirmed redistribution rights, a specific
consumer's configuration or vocabulary, non-deterministic output (lines
28-45). A municipal-ordinance adapter would be judged by the same
principles as the existing `egov_xml`, `json`, `xml`, and `html` adapters,
not exempted from them. The profile's
["Exclusions"](jlegal-okf-profile-0.1.0-draft.md#exclusions) section already
names municipal ordinances in the excluded set and states that "[f]uture
capabilities require a separately reviewed profile revision and must not
mutate source or canonical data"
(`docs/jlegal-okf-profile-0.1.0-draft.md:415-419`);
`docs/oss-release/scope-inventory.md` ("Out of scope for v0.1") repeats this
without narrowing it further.

Structurally, the codebase already isolates the parts that would have to
change from the parts that would not:

- **Adapters are already pluggable.** `AdapterRegistry.register`/`.adapt`
  (`src/jlegal_okf/adapters.py` `AdapterRegistry`) dispatches to a named adapter by
  sniffing or explicit `name=`; `default_registry()`
  (`src/jlegal_okf/adapters.py` `default_registry()`) registers `json`, `xml`, `html`,
  and `egov_xml` side by side, each producing the same `Adaptation`
  container (`src/jlegal_okf/adapters.py` `Adaptation`). A municipal-ordinance
  adapter would register the same way, without touching `egov_xml_adapter`
  itself.
- **The canonical model is already adapter-agnostic.** `LegalNode`,
  `NodeKind`, `SourceRef`, and `Temporal` (`src/jlegal_okf/model.py`) carry
  no e-Gov-specific field; `NodeKind` already includes structural kinds
  (`PART`, `CHAPTER`, `SECTION`, `ARTICLE`, `PARAGRAPH`, `ITEM`, `SUBITEM`,
  `APPENDIX`, `TABLE`, ...) that a municipal ordinance's structure would
  largely reuse rather than require new kinds for, and `jurisdiction`/
  `authority` (`src/jlegal_okf/model.py` `LegalNode`) are already free-text,
  normalized inputs rather than hardcoded to national law.
- **Validation and export are already generic over adapter identity, with
  one explicit, adjustable gate.** `validate_corpus`
  (`src/jlegal_okf/validation.py`) runs the same structure/source-fidelity/
  semantic checks regardless of which adapter produced the nodes. The one
  place adapter identity is checked at all is `_require_egov_profile_corpus`
  (`src/jlegal_okf/legal_okf.py` `_require_egov_profile_corpus()`), which restricts *this profile's*
  OKF export specifically to `egov_xml`-sourced corpora — precisely the kind
  of single, named, reviewable gate a new profile revision would adjust,
  rather than a scattered assumption threaded through the pipeline.
